# 팀 개발 협업 규칙과 결정 기록

**상태:** 팀 합의용 초안  
**기준 문서:** [PRD](../PRD.md) · [개발 문서 안내](README.md)

## 1. 함께 일하는 방식

1. 작업 전 [구현 백로그](IMPLEMENTATION_BACKLOG.md)의 `DEV-xx` 하나를 선택하고 담당자·리뷰어를 정한다. 같은 데이터·API를 수정하는 두 작업은 순서와 계약을 먼저 합의한다.
2. 코드는 짧은 작업 브랜치에서 변경한다. 브랜치 이름 예: `feat/dev-04-application-form`, `fix/dev-08-email-retry`.
3. 한 PR은 하나의 사용 가능한 흐름 또는 명확한 수정 범위를 담는다. PRD·API·DB 계약을 바꾸면 관련 문서도 같은 PR에 넣는다.
4. 작성자는 자기 PR의 테스트와 주요 화면을 직접 확인한 뒤 리뷰를 요청한다. 리뷰어는 정상 흐름뿐 아니라 권한 거절·마감·중복 제출을 확인한다.
5. 리뷰에서 발견한 이견은 코드 코멘트에 남기고, 제품 결정이 필요한 경우 아래 결정 기록에 옮긴다. 채팅에서만 결정하고 문서를 그대로 두지 않는다.
6. 병합 후 팀 공용 테스트 환경에서 핵심 흐름을 확인한다. 배포가 필요한 변경은 적용한 버전과 확인한 URL·시각을 PR에 남긴다.

## 2. 역할과 책임

| 역할 | 책임 | 현재 상태 |
| --- | --- | --- |
| 제품 결정 담당 | PRD 범위·우선순위·사용자 문구 승인 | 팀에서 지정 |
| 기술 결정 담당 | 스택·데이터 모델·권한 정책 승인 | 팀에서 지정 |
| 작업 작성자 | 구현, 문서 갱신, 검증 증거 제출 | 작업별 지정 |
| 리뷰어 | 계약·권한·UX·테스트 확인 | 작업별 지정 |
| 시범 운영 담당 | 실제 제작자·배우 모집, 사용성 테스트, 결과 정리 | 팀에서 지정 |

한 사람이 여러 역할을 맡아도 된다. 배우 개인정보를 다루는 변경은 작성자 외의 사람이 접근 거절 사례를 확인한다.

## 3. PR 완료 기준

- [ ] 연결된 PRD 요구사항과 백로그 작업이 명시되어 있다.
- [ ] 새 기능의 정상 흐름과 중요한 실패 흐름이 작동한다.
- [ ] 권한 검사와 데이터 노출 범위를 확인했다.
- [ ] 타입·린트·관련 테스트·빌드가 통과한다. 실제 명령은 코드 생성 후 이 문서에 기록한다.
- [ ] 화면 변경을 iPhone·Android의 휴대전화 폭에서 확인하고 캡처를 첨부했다. 넓은 화면 확인은 보조다.
- [ ] DB 변경에는 마이그레이션과 기존 데이터 영향 설명이 있다.
- [ ] 사용자에게 보이는 문구는 제품 목적과 다음 행동이 분명하다.
- [ ] API·상태·우선순위가 바뀌었다면 해당 문서를 갱신했다.

## 4. 의사소통과 이슈 기록

이슈에는 `문제/목표`, `관련 Rxx·DEV-xx`, `수용 기준`, `의존성`, `디자인 또는 API 참고`, `담당자`, `상태`를 적는다. 상태는 `대기 → 진행 → 리뷰 → 검증 → 완료`로 관리한다. 막혔을 때는 원인과 필요한 결정을 이슈에 남기며, 별도 구두 설명 없이 다른 사람이 이어받을 수 있도록 한다.

주 1회 짧은 제품·개발 점검에서 (1) 완주 가능한 사용자 흐름, (2) 다음 병목, (3) 결정이 필요한 항목, (4) 시범 운영 증거를 확인한다. 회의 날짜보다 코드·사용자 검증 상태를 기준으로 다음 작업을 고른다.

### Codex와 함께 작업할 때

- 작업 요청은 `DEV-04 구현`처럼 백로그 ID를 지정한다. Codex는 관련 PRD 요구사항과 이 문서의 결정을 확인한 뒤 코드·테스트·문서를 함께 갱신한다.
- 디자인이나 API를 바꾸려면 `R03 지원서 필드 변경`처럼 영향 받는 요구사항을 함께 적는다. 결정이 비어 있으면 가능한 작업부터 진행하고 필요한 선택을 문서에 표시한다.
- 리뷰 요청은 PR 또는 변경 파일 범위와 확인하고 싶은 위험을 적는다. 예: `DEV-08 결과 알림에서 중복 발송과 권한을 리뷰`.
- 작업 완료 보고에는 변경 내용, 실행한 검사, 직접 확인한 화면·경로, 남은 위험과 다음 작업 ID를 남긴다.

| --- | --- | --- | --- |
| D01 | 웹·서버·DB·파일·배포 스택 | [Next.js + Supabase 권장안](STACK_PROPOSAL.md)을 검토 | 미정 |
| D02 | 배우의 첫 지원·본인 재접속 인증 | 앱 설치 없이 이메일 링크로 본인 확인. 지원 시작 전/제출 직전 인증 시점 테스트 | 미정 |
| D03 | 사진·연기 영상 입력 범위 | 사진은 비공개 저장소 업로드, 영상은 검증된 URL 입력 우선 | 미정 |
| D04 | 동일 배역 중복 지원과 수정 | 제출 전 임시 저장, 제출 후 수정 정책을 명시. 덮어쓰기 금지 | 미정 |

| D07 | 제작자 신원 확인 | 초기에는 이메일 확인, 재학·제작 이력 인증은 인터뷰 후 결정 | 미정 |


## 6. 문서 관리

- PRD는 사용자 문제와 기능 범위의 기준이다. 제품 방향이 바뀌면 PRD의 관련 R번호부터 수정한다.
- 기술 설계는 시스템 경계, 데이터와 API 계약은 프런트·백엔드 합의, 백로그는 실행 순서의 기준이다.
- 스택 승인 전에는 제공자 전용 코드나 스키마 파일을 만들지 않는다.
- 오래된 결정도 지우지 않고 `대체됨`으로 표시해 이유를 남긴다.
